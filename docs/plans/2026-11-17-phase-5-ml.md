# Phase 5 — Machine Learning on Photos Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Every photo gets a CLIP image embedding and a few zero-shot tags ("beach", "dog", "snow", "birthday cake"); the user can search their photos by free text **in English** ("dog on the beach"; French queries are not supported by the chosen model), combined with the timeline filters (place, person, tag, camera, kind). Faces are detected, embedded and grouped into people the user can name, merge, split, hide and correct; the whole face feature can be turned off per user, which deletes that user's face data. Explore gains People, Places and Tags pages. All of it runs on the CPU of a home mini PC, in the background, below thumbnails in priority, from models the operator installs with a script and the worker verifies by SHA-256. **Images only:** video keyframes are Phase 4's job (see "How Phase 4 plugs in").

**Architecture:** A new `squirrel-ml` crate holds pure inference code: image preprocessing (from the `preview` WebP the thumbnails step already made, never the original), the CLIP image and text encoders, the face detector, 5-point alignment and the face recognizer, all through ONNX Runtime (`ort`, dynamically loaded, pinned library). Inference runs in a **long-lived `squirrel ml-exec` child process** (rlimits, JSON-lines protocol, restarted on crash, after N requests and when idle), so a fault in ONNX Runtime never takes the worker down and models load once, not per photo. New job kinds in `squirrel-worker`: `clip_embed:<sha256>` (content-derived, shared by every owner of the blob), `faces:<sha256>` (one inference per blob, rows written **per owner** that has faces on) and `cluster_faces:<owner_id>` (per user, debounced to at most every 10 minutes, incremental). Embeddings live in pgvector (`halfvec(512)`, cosine, exact owner-scoped scans). Text search encodes the query with the text tower in an `ml-exec` child **of the server**, started on the first search and stopped after 5 idle minutes (the text tower is 254 MB, ≈ 0.4 GB RSS), and ranks by an exact cosine scan scoped to the caller's own assets through the same `assets ⋈ nodes` join as the timeline. The SPA gains `/search`, `/explore/{people,places,tags}`, `/explore/people/[id]`, timeline filter chips and Settings › Faces.

**Tech Stack:** Phase 3 stack, plus (all listed again under "Open questions" for approval): `ort` `=2.0.0-rc.15` (MIT/Apache-2.0; features `load-dynamic`, `ndarray`; no build-time download) with Microsoft's ONNX Runtime **1.31.1** CPU build (MIT) fetched and SHA-256-checked by `scripts/fetch-onnxruntime.sh`; `tokenizers` (Hugging Face, Apache-2.0, `onig` off) for the CLIP text tokenizer; `ndarray` (re-exported by `ort`); pgvector **0.8.7** (already in the `pgvector/pgvector:pg17` image, verified below). Clustering is hand-written (≈ 150 lines, see "Clustering"). Web: no new npm dependency (Places map: Open question 9).

**Design reference:** `docs/plans/2026-11-13-squirrel-home-drive-design.md` (sections "Media pipeline" items 4–6, "Web UI", "Delivery phases").
**Phase 3 reference:** `docs/plans/2026-11-14-phase-3-media-pipeline.md`, especially "How Phase 4 (video) and Phase 5 (ML) plug in", whose seams this plan follows (the deviations are listed under "Key decisions" with their reason). The code is the source of truth, not that plan's snippets.

## As built — Milestone A review fixes (2026-11-18)

- **ML never stops the worker** unless `--kinds` names ML kinds. A start-up failure is logged at error level, and the ML kinds are not registered.
  - Each worker host records its outcome in `ml_worker_status` (migration `20261118000002_ml_status.sql`; with `20261118000003_label_banks.sql` below, **the faces migration becomes `20261118000004`**).
  - `GET /api/media/status` gains `ml: {state: ready | unavailable, reason}`, with fixed reasons: "models not installed", "ONNX Runtime not configured", "model files do not match their pins", "the inference process failed to start", "no worker has reported".
- **Supervisor:**
  - After a failed start it refuses new starts for 30 s, doubling up to 10 min. Requests meanwhile get `Backoff`, which `clip_embed` turns into `JobError::Reschedule`, so no attempt is spent.
  - A request cancelled mid-exchange leaves a `busy` flag set, and the next request replaces that child.
  - Waiting for the child is bounded by one start plus one request, after which the request fails with a retryable `Busy`.
  - Child log lines are limited to 20 a minute.
  - The child is stopped right after the start-up health check.
- **pgvector:** when the extension is missing, the start-up check runs `CREATE EXTENSION IF NOT EXISTS vector`. SQLSTATE 42501, 58P01 and 0A000 map to messages that name the database, and version 0.7 or later is required.
- **Models are hashed in memory and loaded from that same buffer** (`commit_from_memory`). This closes the window between the check and the load, but the child's start-up peak RSS goes from 454 MB to 804 MB. The models directory and the ONNX Runtime library must be read-only to the service user (README).
- **`--ml-concurrency` accepts only 1 for now:** one child serves one request at a time. A `--kinds` selection that leaves nothing runnable is refused, and `noop` must be listed for `admin jobs ping`.
- **Assets moved:** the downloaded runtime and models now live in `.cache/squirrel-assets/{onnxruntime,onnxruntime-cache,models}` (gitignored), not under `target/`.
  - CI caches the extracted library and the models separately, each keyed by its fetch script, with restore-keys.
  - `fetch-onnxruntime.sh` skips an install whose marker matches, and swaps a new install in with renames.
  - Both scripts bound and retry `curl`.
- **Sandbox gap** (Milestone A as built; to revisit with Phase 7's container):
  - `ml-exec` and `media-exec` run as the worker's uid, with network access.
  - They can read every blob and the whole data directory. They inherit only `PATH` and run with rlimits.
  - On Linux they also set `no_new_privs`.
  - There is no seccomp, namespace or filesystem confinement yet.

## As built — Milestone B (2026-11-18)

- **Schema** (`20261118000001_ml.sql`) is the plan's, with two additions:
  - `clip_embeddings.tagged_labels_version` (NULL = not tagged yet) drives backfill rule 4 (re-tag only) instead of reading `asset_tags`. A blob may legitimately have no tag at all.
  - Existing non-image `media` rows start with `clip_state` and `faces_state` = `unsupported`.
- **Text tower brought forward** from Task 13: the label bank needs it. `tokenizers` runs with `default-features = false, features = ["fancy-regex"]`. With neither `onig` nor `fancy-regex` the crate refuses to build, because the CLIP pre-tokenizer is a regex. The tokens match OpenAI's (`a photo of a dog.` → 320 1125 539 320 1929 269). Inputs are framed `<|startoftext|>` … `<|endoftext|>` and padded to 77 with `<|endoftext|>` (49407). The model's input type is read from the session.
- **Preprocessing:** `fast_image_resize` CatmullRom (PIL's bicubic), shortest side to 224 with torchvision's truncation, then a centre crop with torchvision's rounding. `PreprocessCfg` is parsed from `preprocess_cfg.json`, and unknown modes are refused.
- **Golden test:** a unit test (`clip/golden_tests.rs`) instead of `tests/clip_golden.rs`, so it can use `testutil` without the feature. `make_golden` writes `tests/fixtures/clip/golden-openai-vit-b32-224.json`. No `shapes.json`: the generator is code (`testutil::shape_image`).
- **Label bank:** `labels-v1.tsv` has 202 English labels (no French column). Templates are the plan's 7. That makes 1 414 prompts, computed once at worker start by a short-lived `clip-text` child: 24.7 s on an M4 Pro. Without the text tower, photos get embeddings but no tags.
- **Thresholds are PROVISIONAL:** probability ≥ 0.20 and cosine ≥ 0.24, top 5. They were set on generated pictures only, because no real photo library was available (the phone server's data is off-limits).
  - On the shapes: blue square → `flag` 0.47; green triangle → `christmas` 0.79; red circle → `flag` 0.68 and `sushi` 0.145 (cut).
  - Task 11's calibration on ~200 real photos (`--example tag_report`) is still to do.
- **`thumbnails` → `clip_embed`:** after an image's preview is recorded, `clip_embed` is queued at `CLIP`, or at `background(CLIP)` when the thumbnails job came from backfill. `JobContext` now carries the job's `priority` for this.
- **Backfill** (only on a worker that runs `clip_embed`):
  - Rule 1: images with a ready preview, `clip_state = 'pending'` and no embedding.
  - Rule 4: embeddings whose `tagged_labels_version` differs from the current one, and only once a bank exists.
  - Also marks `clip_state = 'unsupported'` for images whose thumbnails failed or are unsupported.
- **Measured** (Apple M4 Pro, release, 2 inference threads, `ml_concurrency` 1):
  - `examples/bench`, 200 generated 1440 × 960 JPEGs (medians): decode 3.2 ms, preprocess 1.9 ms, image encoder 13.3 ms. Peak RSS 460 MB.
  - `tests/ml_throughput.rs` (ignored, by hand), 40 generated photos through the real pipeline (sandboxed thumbnails, `ml-exec` child):
    - All embedded and tagged 6.1 s after the backfill was queued. The first CLIP result came after 4.7 s, because every thumbnail runs first.
    - `clip_embed` handler wall time: median 35.7 ms, p90 36.9 ms, 1.2 s for the first call (cold child start).

### Face detection and recognition — licences first

- **InsightFace** (SCRFD, ArcFace, `buffalo_l`, `antelopev2`): the README says "The code of InsightFace is released under the MIT License", **but** "The training data containing the annotation (and the models trained with these data) are available for **non-commercial research purposes only**", and "Both manual-downloading models from our github repo and auto-downloading models with our python-library follow the above license policy". The model zoo: "**ALL models are available for non-commercial research purposes only.**" Immich ships them only under a permission "granted via email by Jia Guo" (18 March 2023) which, in Immich's own words, "**does not extend to the redistribution or commercial use**". That permission is Immich's, not ours: **Squirrel's fetch script must not download InsightFace models.** (The design doc's "SCRFD + ArcFace" predates this check.)
- **Permissive pair from OpenCV Zoo:**
  - **YuNet** detector: "All files in this directory are licensed under MIT License." ≈ 233 kB; `face_detection_yunet_2026may.onnx` is the current default (same weights as 2023mar, re-exported for any input size). Box + score + **5 landmarks**. WIDER FACE val 0.884 / 0.866 / 0.750 (easy/medium/hard). Finds faces from ~10 to ~300 px, so input is downscaled first. Raw outputs (cls, obj, bbox, kps at strides 8/16/32) are decoded by us, following OpenCV's `face_detect.cpp`: score `sqrt(cls·obj)`, centre `(col + b0)·stride`, size `exp(b2)·stride`, landmarks `(kps + col)·stride`, then NMS.
  - **SFace** recognizer: "All files in this directory are licensed under Apache 2.0 License." 38.7 MB (int8 9.9 MB), MobileFaceNet with the SFace loss, **128-d**, LFW 99.40 %; OpenCV's match threshold is cosine similarity ≥ **0.363**. Input: the 112 × 112 aligned crop, RGB 0–255, no normalisation. Training data of the released weights not stated (the paper used CASIA-WebFace, VGGFace2, MS-Celeb-1M).
  - Upgrade path: **EdgeFace** (BSD-3-Clause weights, LFW 99.83 % for `base`, 99.73 % for the 1.8 M-parameter `xs_gamma_06`; PyTorch weights, **no official ONNX export**: we would export it ourselves and pin our file).
- **Accuracy trade-off:** `buffalo_l` LFW 99.83 / IJB-C 97.25; InsightFace MobileFaceNet 99.70 / 95.02; SFace 99.40 / no IJB-C published. Expect SFace to be weaker on profile, small and low-light faces: **more, smaller clusters** for the same person, which the merge UI absorbs.
- **Dataset caveat:** nearly every recognizer was trained on retracted or research-only face datasets (MS1M retracted, VGGFace2 withdrawn, Glint360K/WebFace research-only). A permissive weights licence does not settle that; OpenCV distributing YuNet and SFace under MIT/Apache is the cleanest position available.
- **Alignment:** OpenCV's `FaceRecognizerSF::alignCrop` maps the 5 landmarks onto the ArcFace template `(38.2946, 51.6963), (73.5318, 51.5014), (56.0252, 71.7366), (41.5493, 92.3655), (70.7299, 92.2041)` with a similarity transform and warps to 112 × 112, bilinear. The same template serves EdgeFace/ArcFace (which expect `(x − 127.5) / 127.5` instead).

Sources: https://github.com/deepinsight/insightface (README and model_zoo) · https://huggingface.co/immich-app/buffalo_l · https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet · https://github.com/opencv/opencv_zoo/tree/main/models/face_recognition_sface · https://github.com/otroshi/edgeface · https://github.com/zhongyy/SFace.

### Clustering

| Crate | Version | Licence | Algorithms | Cosine |
|---|---|---|---|---|
| `petal-clustering` | 0.14.0 | Apache-2.0 | DBSCAN, HDBSCAN, OPTICS | yes, generic metric |
| `hdbscan` | 0.12.0 | MIT/Apache-2.0 | HDBSCAN | no (Euclidean etc.) |
| `linfa-clustering` | 0.8.1 | MIT/Apache-2.0 | DBSCAN | no built-in cosine |

On L2-normalised vectors squared Euclidean distance is `2 − 2·cos`, so any Euclidean implementation ranks like cosine. A full HDBSCAN over 50k faces is ~1.25 billion pair distances: fine as a rare batch, wrong for every upload. **Immich** clusters incrementally with pgvector (`person.service.ts`): for each unassigned face, the `minFaces` nearest faces within `maxDistance` (cosine, defaults 0.5 and 3, buffalo_l); a face with ≥ `minFaces` neighbours is "core"; it takes the person of the first neighbour that has one, else of the nearest assigned face within `maxDistance`, else a core face founds a new person; non-core faces are deferred once and retried by a nightly job. Source: https://docs.immich.app/features/facial-recognition, https://docs.immich.app/install/config-file.

### pgvector

- **0.8.7** is the latest release and what `pgvector/pgvector:pg17` holds today (`0.8.7-pg17`, digest `sha256:b513c48566e4777cd3370451400000c78eda6a08131d68f4c31d4a76f27bd8fd`, pushed 2026-11-12). The `pg17` tag moves: pin the versioned tag and digest (Task 6).
- `vector`/`halfvec` hold up to 16 000 dimensions; indexes take `vector` ≤ 2 000 and `halfvec` ≤ 4 000. Row size: `vector` 4·d + 8 B, `halfvec` 2·d + 8 B. A `vector(768)` (3 080 B) is TOASTed out of line; a **`halfvec(768)` (1 544 B) stays inline** and halves the I/O.
- HNSW: better speed/recall than IVFFlat, slower to build, can be built empty; defaults `m = 16`, `ef_construction = 64`, `hnsw.ef_search = 40`. **Filtering happens after the index scan** ("if a condition matches 10 % of rows … only 4 rows will match on average"); 0.8.0 added `hnsw.iterative_scan = strict_order | relaxed_order` bounded by `hnsw.max_scan_tuples` (default 20 000), with a `MATERIALIZED` CTE + `ORDER BY d + 0` to restore exact order on Postgres 17. The README warns that "sharing an approximate index between tenants means vectors from one tenant can affect recall (and speed) for other tenants", and that "exact indexes work well for conditions that match a low percentage of rows".
- Exact scans: the planner ignores TOAST in its costs (another reason for inline `halfvec`); parallel workers help.

Source: https://github.com/pgvector/pgvector · https://hub.docker.com/r/pgvector/pgvector/tags.

## Key decisions (read before starting)

### Runtime and sandbox

| Topic | Decision | Why |
|---|---|---|
| Inference runtime | **`ort` `=2.0.0-rc.15` + ONNX Runtime 1.31.1 (CPU execution provider)**, `default-features = false`, features `load-dynamic`, `ndarray`; the exact pin is required because `ort` is a release candidate whose API still moves between rcs. The library is **not** downloaded by the build: `scripts/fetch-onnxruntime.sh` fetches Microsoft's official release archive (`onnxruntime-{linux-x64,linux-aarch64,osx-arm64}-1.31.1.tgz`) for the platform, checks the version with `ort::util::probe` at start, checks a pinned SHA-256, unpacks into `target/onnxruntime/` (dev, CI) or the Docker image (Phase 7); the worker gets `SQUIRREL_ORT_DYLIB` (→ `ort::init_from(path)`). CoreML is **not** used (dev-only platform, and its results differ slightly from CPU, which would break golden tests). | Fastest CPU inference of the options and runs every export as is (Research summary). Dynamic loading keeps the pin and the verification in our hands, exactly like pdfium; `ort`'s default download comes from a third-party CDN at build time, which we refuse. |
| Threads | One intra-op thread pool per session, `intra_threads = SQUIRREL_ML_THREADS` (default `max(1, cores / 2)`), inter-op 1, `GraphOptimizationLevel::Level3`, memory arena on. ML jobs are claimed **one at a time** by default (`--ml-concurrency 1`, Task 4): a single inference already uses several cores. | Two ML jobs with 4 threads each on a 4-core box would starve the web server and thumbnails. |
| Where inference runs | **A long-lived `squirrel ml-exec` child** per worker (hidden subcommand), speaking JSON lines on stdin/stdout: `{"op":"clip_image","input":"…/preview-v1.webp"}` → `{"status":"ok","embedding":[…]}`. It applies rlimits before loading anything: `RLIMIT_AS` **4 GiB** on Linux (image tower 352 MB + faces ≈ 40 MB of weights; ONNX Runtime arenas and thread stacks reserve address space well beyond RSS, so Task 5 measures the peak and sets the final value with 50 % headroom), `RLIMIT_CPU` none (long-lived; the parent enforces a 60 s per-request wall clock instead), `RLIMIT_NOFILE` 64, `RLIMIT_CORE` 0, `RLIMIT_FSIZE` 0 (it writes nothing). The parent restarts it on crash, protocol error or timeout, after **1 000 requests** (bounds fragmentation) and after **10 idle minutes** (frees ~1 GB of RAM on a home box). `SQUIRREL_ML_EXEC=in-process` for tests. (**Open question 10**.) | The untrusted input is a WebP **we** encoded, decoded by `image`'s pure-Rust WebP decoder, then fixed-size tensors: a small attack surface. The real risk is a C++ fault or memory blow-up in ONNX Runtime; a separate process contains it. Per-job children (the `media-exec` model) would reload ~350 MB of models for every photo (≈ 1–2 s, more than the inference). |
| Models on disk | `<data_dir>/models/<name>/<file>` (or `SQUIRREL_MODELS_DIR`), each file listed in `squirrel_ml::models::PINNED` (name, relative path, size, SHA-256, licence, source URL + revision). The `ml-exec` child **re-hashes every model file before loading it** (≈ 1 s per 300 MB, once per child start) and refuses a mismatch. `SQUIRREL_MODELS_DIR` set by an operator is still verified (unlike `SQUIRREL_GEODATA_FILE`): a model is code-like. | Phase 3 decision: the worker never downloads anything. A pinned hash checked at load time also catches a corrupted disk. |
| Fetching | `scripts/fetch-models.sh [dest]`: `curl --proto '=https' --tlsv1.2` from the Hugging Face **revision-pinned** URL (`https://huggingface.co/<repo>/resolve/<commit>/<path>`), SHA-256 checked before moving into place, `LICENSE`/`NOTICE` files fetched alongside and kept next to the models, a `.squirrel-models` marker as in `fetch-pdfium.sh`. Faces are a separate group (`--without-faces` skips them). | Revision pins make the URL immutable; the hash makes it verified. |
| Without models | Handlers register only when their models are installed and verified at worker start: `clip_embed` needs `clip`, `faces` needs `faces`. Jobs for unregistered kinds stay queued (the queue never claims them). Backfill queues ML jobs **only from a worker that registered them**, so an install without models accumulates only fresh uploads' ML jobs, and installing the models later fills in the rest at the next worker start. | No error spam, no wasted rows, and "install models then restart" just works. |
| Separate ML machine | `squirrel worker --kinds clip_embed,faces,cluster_faces` (new allowlist) on a bigger machine sharing the data directory **read-only** (it reads `derived/` previews and writes only to Postgres); the main worker gets `--exclude-kinds clip_embed,faces,cluster_faces`. | Phase 3 seam. ML writes nothing to disk, so a read-only mount suffices. |

### Jobs

| Kind (dedupe key) | Enqueued by | Priority (fresh / backfill) | Timeout | What it does |
|---|---|---|---|---|
| `clip_embed` (`clip_embed:<sha>`) | the `thumbnails` handler after installing an image's previews; backfill | **−25 / −75** | 90 s | Decodes `preview-v<N>.webp` (≤ 1440 px, pure-Rust decoder, pixel cap), resizes the shortest side to 224 then centre-crops 224 × 224 (bicubic, `resize_mode: shortest`), normalises with CLIP's mean `(0.48145466, 0.4578275, 0.40821073)` and std `(0.26862954, 0.26130258, 0.27577711)`, runs the image encoder, L2-normalises, stores `clip_embeddings(sha256, model, embedding)`; then scores the embedding against the label bank (`clip_label_embeddings`, a 200 × 512 matrix product in Rust, < 1 ms) and replaces the blob's `asset_tags` rows of source `clip`. Sets `media.clip_state`. If an embedding for the current model already exists (label bank changed), it only re-tags. |
| `faces` (`faces:<sha>`) | the `thumbnails` handler (only if at least one owner of the blob has faces on); backfill; turning faces on | **−30 / −80** | 120 s | Runs YuNet on the preview downscaled to 640 px on its long side (YuNet sees faces of ~10–300 px), maps boxes and landmarks back to the 1440 px preview, keeps faces with score ≥ 0.6 and short side ≥ 40 px **in the preview**, aligns each to 112 × 112 from the preview, embeds with SFace, L2-normalises; then **for each owner of a live asset with this blob who has faces on and no `face_scans` row for this model**, inserts `faces` rows (box relative 0–1 to the displayed image, landmarks, score, embedding) and a `face_scans` row (also when no face was found), and queues `cluster_faces:<owner>` with a 10-minute delay. Nothing is stored for owners with faces off. Sets `media.faces_state` (the inference step, not per-owner data). |
| `cluster_faces` (`cluster_faces:<owner_id>`) | `faces` (delay 10 min), people edits that unassign faces (delay 1 min), turning faces on | **−35** | 5 min | Incremental clustering of the owner's unassigned `auto` faces (see "Clustering"). The dedupe key collapses every request made while one is queued, so it runs at most once per 10 minutes per user during an import. |
| `face_backfill` (`face_backfill:<owner_id>[:<after>]`) | turning faces on | **−80** | 60 s | Pages through the owner's assets (500 at a time) queuing `faces:<sha>` where the owner has no `face_scans` row. |

- **Priorities.** New constants in `squirrel_jobs::priority`: `CLIP = -25`, `FACES = -30`, `CLUSTER = -35`; backfill subtracts the existing `BACKGROUND_PENALTY` (50). The lowest Phase 3 value is `background(GEOCODE) = -20`, so **every ML job runs after every Phase 3 job, fresh or backfilled**. A unit test pins the order: fresh Phase 3 > backfilled Phase 3 > fresh CLIP > fresh faces > cluster > backfilled ML.
- **ML slots.** `WorkerConfig` gains `ml_kinds` and `ml_concurrency` (default 1, `--ml-concurrency`, `SQUIRREL_ML_CONCURRENCY`): the claim asks for ML kinds only while fewer than `ml_concurrency` ML jobs run, so with the default `concurrency = 2` one slot is always free for a fresh upload's thumbnails. Priority alone is not enough: without slots, a 50k backlog keeps both slots busy and a fresh upload waits for a running inference to end (≈ 1 s, acceptable) but also competes for CPU with two inferences. Task 4.
- **Prerequisites.** Both ML handlers need `thumbs_state = 'ready'` and the current preview file; if thumbnails are `pending` they `Reschedule(5 min)` (no attempt used); `failed`/`unsupported` → the ML step is marked `unsupported` with that reason.
- **Domain failures are not job errors** (Phase 3 rule): an undecodable preview → `clip_state = 'failed'`, job `Ok`.
- **Backfill rules** (added to `requeue_stale_steps`, only when the worker registered the kind):
  1. `clip_embed` for image media with `thumbs_state = 'ready'` and no `clip_embeddings` row for the current model;
  2. `faces` for blobs that have a live asset owned by a faces-on user without a `face_scans` row for the current face model;
  3. `cluster_faces` for every faces-on user with unassigned, unlocked faces (one row per user, deduped);
  4. `clip_embed` also when the **label bank** version changed (`asset_tags` re-scored from the stored embedding, no image inference: the handler sees an existing embedding and only re-tags).

```sql
-- FROZEN once merged: never edit; add a new migration instead.
-- Phase 5: CLIP embeddings and tags (content-derived), per-user ML settings.
-- pgvector is not a trusted extension: the migration role must be a superuser,
-- or a superuser must have run CREATE EXTENSION vector beforehand.
CREATE EXTENSION IF NOT EXISTS vector;

ALTER TABLE media
    ADD COLUMN clip_state  TEXT NOT NULL DEFAULT 'pending'
        CHECK (clip_state IN ('pending', 'ready', 'failed', 'unsupported')),
    ADD COLUMN faces_state TEXT NOT NULL DEFAULT 'pending'
        CHECK (faces_state IN ('pending', 'ready', 'failed', 'unsupported'));

-- One CLIP image embedding per blob and model. Content-derived: shared by every
-- owner of the blob, only ever read through the caller's own assets.
CREATE TABLE clip_embeddings (
    sha256     TEXT NOT NULL REFERENCES media (sha256) ON DELETE CASCADE,
    model      TEXT NOT NULL CHECK (char_length(model) <= 64),
    -- OpenAI CLIP ViT-B/32: 512 dimensions. halfvec(512) is 1 032 bytes: stored inline.
    embedding  halfvec(512) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (sha256, model)
);
-- No ANN index on purpose: searches scan the caller's own embeddings exactly
-- (see "Search and filters"). Add HNSW later if libraries outgrow exact scans.

-- Text embeddings of the label bank, per model and labels version.
CREATE TABLE clip_label_embeddings (
    model          TEXT NOT NULL,
    labels_version SMALLINT NOT NULL,
    tag            TEXT NOT NULL CHECK (tag ~ '^[a-z][a-z0-9_]{0,47}$'),
    embedding      halfvec(512) NOT NULL,
    PRIMARY KEY (model, labels_version, tag)
);

-- Zero-shot tags (Phase 5) and, later, other sources. `tag` is a stable English
-- slug from the label bank ('beach', 'dog'); display names are translated in the UI.
CREATE TABLE asset_tags (
    sha256     TEXT NOT NULL REFERENCES media (sha256) ON DELETE CASCADE,
    tag        TEXT NOT NULL CHECK (tag ~ '^[a-z][a-z0-9_]{0,47}$'),
    source     TEXT NOT NULL CHECK (source IN ('clip')),
    score      REAL NOT NULL,
    labels_version SMALLINT NOT NULL,
    PRIMARY KEY (sha256, tag, source)
);
CREATE INDEX asset_tags_tag_idx ON asset_tags (tag, sha256);

-- Per-user ML preferences (one row per user, created lazily; absent = defaults).
CREATE TABLE user_ml_settings (
    user_id        UUID PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
    faces_enabled  BOOLEAN NOT NULL,
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Migration `20261118000002_faces.sql`:

```sql
-- FROZEN once merged: never edit; add a new migration instead.
-- Phase 5: faces and people. Per owner: biometric data is never shared between
-- users, even for a deduplicated blob, and turning faces off deletes it all.
CREATE TABLE people (
    id          UUID PRIMARY KEY,
    owner_id    UUID NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    name        TEXT CHECK (name IS NULL OR char_length(name) BETWEEN 1 AND 100),
    hidden      BOOLEAN NOT NULL DEFAULT FALSE,
    -- Chosen cover face; NULL = the best-scoring face.
    cover_face_id UUID,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT people_id_owner_key UNIQUE (id, owner_id)
);
CREATE INDEX people_owner_idx ON people (owner_id, hidden, name);

CREATE TABLE faces (
    id          UUID PRIMARY KEY,
    owner_id    UUID NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    sha256      TEXT NOT NULL REFERENCES media (sha256) ON DELETE CASCADE,
    model       TEXT NOT NULL,
    -- Relative to the displayed image (0..1), so any thumbnail size can crop it.
    box_x REAL NOT NULL, box_y REAL NOT NULL, box_w REAL NOT NULL, box_h REAL NOT NULL,
    landmarks   REAL[] NOT NULL CHECK (cardinality(landmarks) = 10),
    score       REAL NOT NULL,
    embedding   halfvec(128) NOT NULL,          -- SFace
    person_id   UUID,
    -- 'auto' (clustering may move it), 'user' (pinned to person_id, or pinned
    -- to "nobody" when person_id IS NULL: never clustered again).
    assigned_by TEXT NOT NULL DEFAULT 'auto' CHECK (assigned_by IN ('auto', 'user')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT faces_id_owner_key UNIQUE (id, owner_id),
    CONSTRAINT faces_person_fkey FOREIGN KEY (person_id, owner_id)
        REFERENCES people (id, owner_id) ON DELETE SET NULL (person_id)
);
CREATE INDEX faces_owner_person_idx ON faces (owner_id, person_id);
CREATE INDEX faces_owner_sha_idx ON faces (owner_id, sha256);
CREATE INDEX faces_unclustered_idx ON faces (owner_id, created_at) WHERE person_id IS NULL AND assigned_by = 'auto';
-- No ANN index: neighbour searches are exact, per owner (a few thousand faces).

ALTER TABLE people ADD CONSTRAINT people_cover_fkey FOREIGN KEY (cover_face_id, owner_id)
    REFERENCES faces (id, owner_id) ON DELETE SET NULL (cover_face_id);

-- Which (owner, blob) pairs were scanned with which model (also "no face found").
CREATE TABLE face_scans (
    owner_id    UUID NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    sha256      TEXT NOT NULL REFERENCES media (sha256) ON DELETE CASCADE,
    model       TEXT NOT NULL,
    face_count  SMALLINT NOT NULL CHECK (face_count >= 0),
    scanned_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (owner_id, sha256)
);

-- When an owner's last asset of a blob goes (permanent deletion), its faces and
-- scan go too: no biometric data outlives the photo. Trashed photos keep theirs.
CREATE FUNCTION assets_drop_faces() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM assets WHERE owner_id = OLD.owner_id AND sha256 = OLD.sha256) THEN
        DELETE FROM faces WHERE owner_id = OLD.owner_id AND sha256 = OLD.sha256;
        DELETE FROM face_scans WHERE owner_id = OLD.owner_id AND sha256 = OLD.sha256;
    END IF;
    RETURN NULL;
END;
$$;
CREATE TRIGGER assets_drop_faces AFTER DELETE ON assets
    FOR EACH ROW EXECUTE FUNCTION assets_drop_faces();
```

People with no face left are deleted by `cluster_faces` (unless named: a named person with no face stays, so a rename survives a re-scan). Faces are keyed by `(owner_id, sha256)` rather than node: two copies of the same photo in one drive show one set of faces.

**Deviation from the Phase 3 seam:** it said "faces … keyed by `owner_id`, joined through `assets`" and dedupe `faces:<sha>`. Both kept: the job is per blob (one inference), the rows per owner. Biometric data is never stored for a user who has faces off, and deleting a user's face data is `DELETE … WHERE owner_id = $1`.

### Clustering

**Hand-written incremental DBSCAN-style assignment, Immich's algorithm adapted, neighbours found by exact pgvector queries per owner.** No clustering crate: the incremental pass is ≈ 150 lines over SQL neighbour queries, and a full HDBSCAN on every upload would be the wrong shape anyway. (`petal-clustering` 0.14, Apache-2.0, is the crate to use if a batch HDBSCAN re-cluster is ever wanted.)

Parameters (constants in `squirrel_ml::cluster`, per face model): `MAX_DISTANCE = 0.50` cosine distance (SFace's "same person" threshold is similarity ≥ 0.363, i.e. distance ≤ 0.637; clustering is transitive, so it uses a stricter value), `MIN_FACES = 3`, `MIN_SCORE = 0.7` (detector score to found a person). Task 21 tunes `MAX_DISTANCE` by hand on a real library and records the value.

`cluster_faces(owner)`, one transaction per batch of 200 faces, oldest first, from `faces_unclustered_idx`:
1. For face *f*: `SELECT id, person_id, assigned_by, embedding <=> $f AS d FROM faces WHERE owner_id = $owner AND id <> $f AND (assigned_by = 'auto' OR person_id IS NOT NULL) ORDER BY d LIMIT 16` (exact scan over the owner's faces: 50k × 264 B ≈ 13 MB, a few ms in shared buffers), keep `d ≤ MAX_DISTANCE`.
2. *f* is **core** when it has ≥ `MIN_FACES − 1` neighbours and score ≥ `MIN_SCORE`.
3. Person = the person most neighbours already belong to (ties: the nearest). Faces pinned to nobody (`assigned_by = 'user' AND person_id IS NULL`) are never neighbours that carry a person and are never moved.
4. No neighbour has a person and *f* is core → a new unnamed person with *f* and its unassigned `auto` neighbours.
5. Non-core faces with no person among neighbours stay unassigned; the next run retries them (new faces may make them core). No nightly job is needed: every `faces` run queues a clustering run.
6. Afterwards: delete unnamed people with no face; set no cover (the API picks the best face when `cover_face_id` is NULL).

Manual edits are **pinned** (`assigned_by = 'user'`) and clustering never moves them: assign (`PUT /api/faces/{id}/person`), unassign = "not this person" (pinned to nobody), merge (all faces of the merged people move and become pinned), split (selected faces → a new person, pinned). Hide sets `people.hidden` (hidden people are left out of Explore and filters but keep clustering so new photos of them stay hidden). A new photo of a known person is assigned automatically through step 3. `squirrel admin faces recluster <username>` clears `auto` assignments of that user and re-runs the pass (escape hatch after a threshold change).

### Search and filters

| Topic | Decision | Why |
|---|---|---|
| Ranking query | **Exact scan of the caller's own embeddings**, no ANN index: `SELECT {SUMMARY_COLUMNS}, e.embedding <=> $q AS d FROM assets a JOIN nodes n … JOIN media m … JOIN clip_embeddings e ON e.sha256 = a.sha256 AND e.model = $model WHERE a.owner_id = $caller [AND filters] ORDER BY d, a.node_id LIMIT $offset + $limit + 1`, assembled with `QueryBuilder`. One row per node (two copies of a photo are two results, as in the timeline). | 100 % recall, natural owner isolation (only the caller's rows are ever touched, so another user's library cannot change the caller's results or timing), and the filters compose as plain `WHERE`s. An HNSW index shared by all users post-filters: with a selective owner or tag filter it returns too few rows unless iterative scans are tuned, and pgvector's own README warns that tenants sharing an index affect each other's recall and speed. 50k × `halfvec(512)` inline ≈ 52 MB: estimated 30–100 ms on one core, measured in Task 14 on 50k synthetic rows (target p95 < 300 ms; above that, add HNSW with `relaxed_order` iterative scan as a follow-up). |
| Relevance | Results are cut at a per-model floor (`d ≤ SEARCH_MAX_DISTANCE`, calibrated in Task 14 with the fixture set and a handful of real photos), at most 200, `offset` paging. | CLIP cosine similarities are small (typically 0.2–0.35) and query-dependent: without a floor, every search returns 200 "results". |
| Query encoding | Text → CLIP byte-level BPE (`tokenizers`, `textual/tokenizer.json`; `CLIPTokenizer`, `do_lower_case: true`, vocabulary 49 408), `<|startoftext|>` … `<|endoftext|>`, padded/truncated to **77 tokens** (`model_max_length`) → text tower → L2-normalise. The ONNX input names and whether padding uses id 0 or the end token are read from the model in Task 13 (UNVERIFIED). Done in the server's lazily started text `ml-exec` child (one at a time, semaphore 1, 10 s timeout). `POST /api/search/warmup` (cheap, rate limited) lets the search page start the child when it opens, hiding the 5–10 s cold start. | The text tower costs ≈ 0.4 GB RSS: small, but still not worth keeping resident in a home server's web process when nobody searches. |
| Filters on the timeline | `person` → `EXISTS (SELECT 1 FROM faces f WHERE f.owner_id = a.owner_id AND f.sha256 = a.sha256 AND f.person_id = $p)`; `tag` → `EXISTS (… asset_tags t WHERE t.sha256 = a.sha256 AND t.tag = $t)`; place and camera → `m.place_country_code = $c AND m.place_admin1 = $r AND m.place_name = $n`, `m.camera_make = $mk AND m.camera_model = $md`; `kind` → `a.kind = $k`. The keyset stays on `assets_timeline_idx`. | Post-filters over one owner's index range are cheap at home sizes; measured on 20k assets in Task 15 (target < 50 ms per page with any one filter). |

### Performance budget

Estimates, not measurements (no hardware was run while planning). Anchors: Immich on an Intel i7-8559U NUC (4 cores, no GPU): **ViT-B/32 (the chosen model) image 97 ms**, 124 ms median with two requests at once, text 38 ms, buffalo_l faces 328 ms per photo. YuNet is ≈ 233 kB and SFace a MobileFaceNet, both far lighter than buffalo_l. "Mini PC" = Intel N100 class (4 efficiency cores), assumed ≈ 1.7× slower than the NUC.

|---|---|---|
| Decode 1440 px preview WebP + resize | 25 ms | 40 ms |
| `clip_embed` (OpenAI ViT-B/32 image) | 90–120 ms | 150–200 ms |
| `faces`: YuNet at 640 px + SFace per face (×1.5 faces on average) | 40–60 ms | 70–100 ms |
| Text query (cold child start / warm) | 2–4 s / 30–50 ms | 3–6 s / 50–90 ms |

| Library | ML concurrency 1 (default) | ML concurrency 2 (≈ 1.7× throughput on 4 cores, starves other work) |
|---|---|---|
| 10k photos, NUC | CLIP ≈ 20 min + faces ≈ 12 min | ≈ 20 min |
| 10k photos, N100 | CLIP ≈ 35 min + faces ≈ 20 min | ≈ 35 min |
| 50k photos, NUC | CLIP ≈ 1.7 h + faces ≈ 1 h | ≈ 1.6 h |
| 50k photos, N100 | CLIP ≈ 2.8 h + faces ≈ 1.7 h | ≈ 2.6 h |

Clustering adds seconds per run (exact neighbour queries on a few thousand faces). The initial backfill is a one-off overnight job; afterwards a phone's daily photos take seconds.

**Memory:** worker `ml-exec` child ≈ 0.6 GB RSS while warm (image tower 352 MB fp32 + arena, faces ≈ 100 MB), released after 10 idle minutes; the server's text child ≈ 0.4 GB while warm (text tower 254 MB), released after 5 idle minutes. Immich measures ≈ 1.0 GB for both ViT-B/32 towers together. The worker process itself is unchanged. **Recommended minimum: 4 GB RAM on the box.**

**Lower priority than thumbnails, in practice:** ML priorities are below every Phase 3 job (fresh or backfilled), the worker runs at most `ml_concurrency` (1) ML job at a time so a slot stays free for fresh uploads, and the ML child uses `SQUIRREL_ML_THREADS` (default half the cores). The `ml-exec` child is started with `nice 10` (`setpriority` before loading) so the web server and thumbnails win CPU contention.

## How Phase 4 (video) plugs in

- **Keyframes.** Phase 4's `thumbnails` for a video extracts its poster frame; for ML it also writes **3 keyframes** (`keyframe-{0,1,2}-v1.webp` at 10 % / 50 % / 90 % of the duration, 1440 px) into the same `derived/ab/cd/<sha>/` directory. `squirrel_ml::input::frames_for(media)` returns `[preview]` for images and the keyframes for videos; that is the only switch.
- **`clip_embed` for videos:** embeds each keyframe and stores their **mean, re-normalised** as the blob's single embedding (search and tags then work unchanged). `clip_embeddings` keeps one row per `(sha256, model)`.
- **`faces` for videos:** runs on each keyframe; faces of one video are deduplicated by embedding distance (< 0.3 cosine distance between keyframes = same face) before writing rows. `faces` gains nothing: the box is relative to the keyframe it came from, so Phase 4 adds a nullable `frame SMALLINT` column (new migration) for the crop endpoint.
- **Backfill:** Phase 4's backfill creates `assets` rows for videos and their `thumbnails` job; the thumbnails handler then enqueues `clip_embed`/`faces` exactly as for images. The ML stale rules above already select by `media.kind IN ('image')`; Phase 4 widens that list to include `'video'`.
- **Filters:** `kind=video` joins the `kind` enum; nothing else changes.

## Security considerations

| Threat | Mitigation in this plan |
|---|---|
| **Cross-user leakage through shared embeddings** | `clip_embeddings` and `asset_tags` are keyed by content but only ever reached from `assets a WHERE a.owner_id = $caller` joined to live `nodes`; search, tags, places and cameras lists use that join before any content table; an API test seeds the same blob for Alice and Bob with tags and checks Bob sees only his own node, and that Bob's search ranking/count is independent of Alice's library. Faces/people are per owner with composite foreign keys `(person_id, owner_id)`, so a face can never point at another user's person. |
| **Biometric data** | Stored only for users with faces on; deleted in one transaction when turned off; deleted with the photo (trigger) and the user (cascade); never exported in logs (embeddings are not logged; errors carry ids only). Face crops are served only after the owner check, `private`, and cleared on logout like thumbnails. |
| **Model supply chain** | ONNX Runtime and every model file pinned by SHA-256 at revision-pinned URLs, re-verified by the child before loading; licences shipped next to them; no download from the server or worker; `ort` built with `load-dynamic` and no `download-binaries`. |
| **Malicious ONNX files** | Only pinned files load; `SQUIRREL_MODELS_DIR` files are verified too. ONNX Runtime custom-op libraries are never registered. |
| **Inference faults / memory** | Long-lived `ml-exec` child with `RLIMIT_AS` 3 GiB, no core dumps, no file writes, a per-request wall clock, restarts on crash; input is our own WebP decoded by pure-Rust code with a pixel cap. |
| **Search abuse** | `q` ≤ 200 chars, ≤ 77 tokens (truncated), `search_routes` rate limit and 5 s statement timeout; the text encoder runs on the blocking pool with a semaphore of 1 (one encode at a time, ≈ 20–50 ms) so a burst cannot pin every core. |
| **Inferring others' content via timing** | Search cost depends only on the caller's library (owner-filtered scan, see "Search and filters"); HNSW iterative scans are not used for the owner filter. |
| **XSS** | Person names are length-capped, control characters stripped, rendered as text; tag slugs are a fixed vocabulary; face boxes are numbers. |

## As built — Milestone B review fixes (2026-11-18)

- **Label bank as a job:** the bank is a `label_bank` job, not a start-up step.
  - It is deduped per (model, labels version), runs at priority `LABEL_BANK` (−26) and counts as an ML kind for the slots.
  - The worker queues it at start when the bank is missing or stale, and never waits for it.
  - The job has its own `clip-text` child (stopped after 1 idle minute), encodes batches of 32 prompts with a 60 s timeout per batch, then queues the re-tags.
  - Until the bank exists, `clip_embed` stores embeddings without tags.
- **Validation:** every embedding, image or text, must be 512 finite values with a norm of 1 ± 1e-2. An invalid answer goes through `give_up_or_retry`, so `clip_state` ends `failed`. `mean_embedding` refuses embeddings of different lengths. Previews longer than 20:1 are `unsupported`.
- **Tagging scheme (labels v2, `LABELS_VERSION = 2`):**
  - No softmax: a label is kept when its cosine reaches the model's threshold, or the label's own (an optional third TSV column), **and** beats the "background" prompts ("a photo.", "an image.", "a picture.", "a photo of something.") by a margin. At most 5 tags, best cosine first. `asset_tags.score` now holds the cosine.
  - Near-synonyms are merged into one label each: cake (birthday cake, dessert, pastry, ice cream), beach (sea, ocean), night (night sky, city lights), swimming_pool, boat, art (painting, drawing, graffiti), forest, group, portrait, document, bedroom, street. That leaves 185 labels.
  - `examples/tag_report` prints the tags per photo and the share of photos with none.
- **Thresholds are PROVISIONAL:** cosine 0.25, margin 0.045, set on 3 generated shapes and 3 synthetic fixtures. With them, 2 of those 6 pictures get no tag. **Calibration on ~200 real photos is still pending** (the user postponed it).
- **Bank digest:** each stored bank records the SHA-256 of its content (labels file, templates, background prompts) in `clip_label_banks` (migration `20261118000003_label_banks.sql`). A bank with another digest is ignored and computed again. A test pins the digest to `LABELS_VERSION`.
- **New previews:** `set_thumbnails` (a new preview) deletes the blob's CLIP embedding and resets `clip_state` to `pending`, in the same transaction that queues the ML steps. Backfill rule 1 queues every image with a ready preview and no embedding, whatever its state.
- **Two-step `clip_embed`:** the embedding and `clip_state = 'ready'` commit together, and tags are a second transaction. An empty label bank is never cached.
- **`squirrel admin jobs`** marks queued ML kinds "waiting for an ML worker" when no worker host reports ML as ready.
